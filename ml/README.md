# Hybrid Fitness Intelligence Model

Machine learning layer for the **Fitness Habit Analysis & Personalized Workout Recommendation System**.

Two scikit-learn models are trained on a labelled CSV and served to the browser
through a small local API:

| Model | Task | Input | Output |
| --- | --- | --- | --- |
| `RandomForestClassifier` | Classify the trainee's **fitness habit category** | the full habit profile (21 features) | one of 5 habit classes + class probabilities |
| `KNeighborsClassifier` | Recommend a **workout category** | goal, frequency, experience, session length, preferences | 3 ranked workout categories with match scores |

Nothing is hard-coded: every number shown on the dashboard comes from a model
that was fitted on `ml/data/fitness_habits.csv`. If the CSV is too small or
broken, the dashboard says so instead of inventing a prediction.

## 2. Running it

```bash
# one command: trains (if needed) and serves the app + the API
python -m ml.serve
```

Then open **<http://localhost:5000>** — the same dashboard as before, with the
new *Hybrid Fitness Intelligence* card at the bottom.

Useful variations:

```bash
python -m ml.build_dataset       # rebuild the labelled CSV from the raw source
python -m ml.train               # retrain both models and rewrite metrics.json
python -m ml.train --retrain     # force a retrain
python -m pytest ml/tests -q     # run the automated tests
python -m ml.serve --port 8001   # serve on a different port
```

The front-end still works **without** the Python service (open `index.html`
directly, or use `node server.js`): every rule-based page keeps working and the
ML card shows a "model service not reachable" notice.

## 3. The training data

`ml/data/fitness_habits.csv` — **1,733 labelled rows × 33 columns**

### Provenance

1. **Base cohort (real data).** The public
   [Gym Members Exercise Dataset](https://www.kaggle.com/datasets/valakhorasani/gym-members-exercise-dataset)
   by Vala Khorasani — 973 real workout sessions with age, gender, weight,
   height, BMI, body fat %, heart rates, session duration, calories burned,
   water intake, days trained per week and experience level. The raw file is
   cached in `ml/data/raw/` and is downloaded automatically by
   `python -m ml.build_dataset`.
2. **Lifestyle attributes (simulated, seeded).** The public dataset does not
   contain the goal, motivation, diet, sleep or tracking habits that the app
   knows about. Those columns are generated by a seeded simulator
   (`ml/build_dataset.py`) that is *conditioned on the real row* — a trainee
   with 30 % body fat is far more likely to be a fat-loss goal than a trainee
   with 12 %. The planned session length is snapped to the same options the
   profile form offers (30/45/60/75/90 minutes).
3. **Cohort expansion.** 760 fully simulated rows are appended so the rarer
   habit classes (sedentary struggle, overtraining risk) and the home / outdoor
   equipment profiles are represented too.

### Labels

Both labels are produced by transparent rules (`ml/labels.py`) and then given a
small amount of label noise (6 % habit, 4 % recommendation) so the task is not
perfectly separable.

**`habit_category`** (Random Forest target) — first matching rule wins:

1. `sedentary_struggler` — one session or less per week
2. `overtraining_risk` — ≥ 5 planned days with ≤ 6 h sleep and motivation ≤ 6
3. `consistent_athlete` — ≥ 85 % adherence, ≥ 7 h sleep, diet quality ≥ 6
4. `steady_improver` — ≥ 60 % adherence, ≥ 6 h sleep, diet quality ≥ 5
5. `inconsistent_athlete` — everything else

**`recommended_category`** (KNN target):

| Goal | Rule | Category |
| --- | --- | --- |
| endurance | ≤ 3 sessions/week and ≥ 45 min | `endurance_base` |
| endurance | otherwise | `conditioning_intervals` |
| muscle | intermediate/advanced and ≥ 4 sessions/week | `push_pull_strength` |
| muscle | advanced and ≤ 3 sessions/week | `lower_body_focus` |
| muscle | otherwise | `full_body_hybrid` |
| loss | ≥ 4 sessions/week or HIIT preference | `conditioning_intervals` |
| loss | otherwise | `full_body_hybrid` |
| health | mobility preference or ≤ 45 min | `core_stability_mobility` |
| health | otherwise | `full_body_hybrid` |

### Missing values

863 cells (≈ 5 % of the numeric lifestyle columns, ≈ 2 % of three categorical
columns) are deliberately blanked in the CSV so the imputation path is always
exercised. `SimpleImputer(strategy="median")` fills the numeric gaps and
`SimpleImputer(strategy="most_frequent")` the categorical ones.

### Data dictionary (model features)

| Feature | Type | Meaning |
| --- | --- | --- |
| `age`, `height_cm`, `weight_kg`, `bmi` | numeric | body metrics (`bmi` is derived by the API from height + weight) |
| `planned_days_per_week` | numeric | training days the user planned |
| `workouts_per_week` | numeric | training days actually completed |
| `skipped_per_week` | numeric | missed sessions |
| `session_minutes` | numeric | length of one session (30–90) |
| `diet_quality` | numeric | diet self-rating 1–10 |
| `protein_meals` | numeric | meals per day with a protein source |
| `junk_food_per_week` | numeric | junk food / sugary drinks |
| `water_glasses` | numeric | glasses of water (≈ 250 ml) |
| `sleep_hours` | numeric | average sleep per night |
| `daily_steps` | numeric | average daily steps |
| `motivation` | numeric | motivation to train 1–10 |
| `screen_before_bed`, `tracks_progress` | binary | the two check-boxes in the profile form |
| `sex` | categorical | male / female / other |
| `fitness_goal` | categorical | loss / muscle / endurance / health |
| `experience_level` | categorical | beginner / intermediate / advanced |
| `equipment` | categorical | full_gym / basic_gym / home / outdoor |
| `activity_level` | categorical | sedentary / light / moderate / active |
| `preferred_focus` | categorical | strength / cardio / hiit / mobility |

## 4. Preprocessing

Both models are wrapped in a `Pipeline`, so training and inference can never
disagree about how a row is prepared.

```
Random Forest (habit classifier)
  numeric (15)  → SimpleImputer(median)
  binary  (2)   → SimpleImputer(most_frequent)
  categorical(6)→ SimpleImputer(most_frequent) → OneHotEncoder(handle_unknown="ignore")
  classifier    → RandomForestClassifier(n_estimators=300, max_depth=10,
                                          min_samples_leaf=2,
                                          class_weight="balanced", random_state=42)

KNN (workout recommender)
  numeric (3)   → SimpleImputer(median) → StandardScaler
  categorical(5)→ SimpleImputer(most_frequent) → OneHotEncoder(handle_unknown="ignore")
  classifier    → KNeighborsClassifier(n_neighbors=9, weights="distance", p=2)
```

The scaler matters: without it `daily_steps` (thousands) and `workouts_per_week`
(single digits) would dominate the euclidean distance and every neighbour
would be "the person who walks a lot".

### Train / test split

`train_test_split(test_size=0.2, random_state=42, stratify=label)` — 1,386
training rows and 347 test rows for each model, plus a 5-fold
`StratifiedKFold` cross-validation for the stability estimate.

## 6. API

Base URL: `http://localhost:5000/api` (also reachable at `/api` when the page
is served by the same process).

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/api/health` | service status, dataset report, model summary |
| `GET` | `/api/metrics` | the full evaluation report |
| `POST` | `/api/predict` | `{ "profile": { ... } }` → habit class + 3 recommendations |
| `POST` | `/api/train` | retrain both models from the CSV |

Example:

```bash
curl -X POST http://localhost:5000/api/predict ^
  -H "Content-Type: application/json" ^

       \"motivation\":6,\"screenBeforeBed\":true,\"tracksProgress\":true}}"
```

### Insufficient training data

If the CSV is missing, too small, missing columns or has a class with too few
rows, the service answers with `status: "insufficient_data"` and a message
such as:

> Only 1 labelled rows are available (at least 80 required). `habit_category`
> contains a single class, so no model can be trained.

The dashboard then shows a yellow notice instead of a prediction. Thresholds
can be tuned with the environment variables `FHA_ML_MIN_ROWS` (default 80) and
`FHA_ML_MIN_ROWS_PER_CLASS` (default 15). `FHA_ML_DATASET` points the service
at a different CSV.

## 8. Deployment on Vercel

Vercel's Python runtime needs three things, all of which are in the repository:

| Requirement | Where it is |
| --- | --- |
| a Flask entrypoint at the project root | `app.py` (exposes `app`) |
| `requirements.txt` at the project root | `requirements.txt` (the `ml/` one is for development) |
| routing configuration | `vercel.json` |

```bash
npm i -g vercel          # once
vercel                   # preview deployment
vercel --prod            # production deployment
```

The first time, Vercel asks which framework to use — pick **Flask** (it is
detected automatically from `app.py` + `requirements.txt`).

What happens on Vercel:

* The whole project (including `ml/data/fitness_habits.csv` and the trained
  `ml/artifacts/model.joblib`) is bundled into the function.
* Serverless file systems are read-only, so `app.py` sets
  `FHA_ML_READONLY=1`: the model is loaded from the bundled artifact and never
  written back. If the artifact is missing the service simply **retrains from
  the CSV in memory** (about one second) and keeps serving.
* `vercel.json` routes every request to the function, so the dashboard, the
  static assets and `/api/*` are all served by the same Flask app — no extra
  configuration needed.
* The very first (cold) request pays for importing pandas + scikit-learn and
  loading the model, so give it a few seconds. Later requests reuse the warm
  container.

Common Vercel error and its fix:

| Error | Cause | Fix |
| --- | --- | --- |
| `[FLASK_ENTRYPOINT_NOT_FOUND]` | no Flask app in `app.py` / `index.py` / `server.py` / `main.py` / `wsgi.py` / `asgi.py` (or `src/`, `app/`, `api/`) | already fixed — `app.py` is in the repository |
| `ModuleNotFoundError: No module named 'ml'` | the project root is not on `sys.path` | `app.py` inserts its own folder into `sys.path` |
| `No module named 'pandas'` | dependencies not installed | `requirements.txt` must be in the **root** folder |
| The dashboard loads but the ML card says "not reachable" | the API is not on the same origin | the API is served from the same function (`/api/...`) — check that `vercel.json` is present |

## 10. Notes and limitations

* The lifestyle part of the cohort is simulated, because no public dataset
  combines goal, motivation, diet, sleep and tracking habits with physiological
  measurements. The simulator is seeded and documented, and the base rows are
  real — but the labels describe the rule set, not measured clinical outcomes.
* The habit classifier is a *descriptive* aid: it summarises the same profile
  the rule-based engine already analyses, from a different angle (learned
  interactions between features). It is not a medical device.
* The KNN recommender proposes a **category** of training, not a prescription.
  The concrete sessions still come from the rule-based plan generator in
  `assets/js/engine.js`.
* Everything runs locally. The service binds to `127.0.0.1` and no profile
  data leaves the machine.
